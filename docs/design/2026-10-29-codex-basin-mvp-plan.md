# Codex Token 桌宠极简 MVP

> 历史阶段记录。2026-10-29 后续用户明确增加单击收菜、武器抽取与分解兑换；当前范围以 [武器 MVP](2026-10-29-weapons-mvp.md) 为准，以下「不做武器」等约束不再适用于当前版本。

日期：2026-10-29。状态：代码已实施，自动化验收通过，Windows 试用包已生成。本文替代此前的修仙游戏与硬件方案；真实用户试用、独立干净机器与物理多显示器/睡眠验收仍待人工完成。

## 1. 产品定义

一座常驻桌面的修仙聚宝盆，陪用户使用 Codex；真实消耗的 Token 聚成可见的收获。聚宝盆本身就是桌宠，没有猫或其他主角。

极简、围绕 Token 是范围判断标准：功能必须帮助用户看见真实用量，或者感受到桌宠对用量的回应。首版只有桌宠和收获页两个玩家界面，不做修仙经营游戏，也不为硬件预留开发任务。

仙侠只保留在视觉和动作中：青玉聚宝盆、吸纳灵气与灵气入藏。不需要玩家理解境界、灵气换算或物品用途。形象固定为专门制作的聚宝盆，不能复用示例猫替代最终主体。

## 2. 唯一循环

照常使用 Codex → 新增 Token 自动入账 → 聚宝盆亮起 → 点桌宠打开收获页 → 看见本次积累并点“收下” → 桌宠庆祝、回到陪伴状态。

- 唯一累计进度是实际 Token 总量，不再兑换薪火、经验、灵石或抽奖次数。
- 第一笔真实新增即可收获，无最低门槛、每日次数限制或强制等待。
- “收下”只是确认已经看过这批收获。Token 在采集时就保存，不靠点击入账。
- 不点击、不打开页面、不连续签到都不会损失累计；长时间没用 Codex，桌宠只是休息。
- 不主动调用模型制造用量，不奖励无意义重复请求，不设置消耗目标或排行榜。

首版正反馈来自“我的实际使用有了一个可见回应”，不是数值奖励再套一层数值奖励。

## 3. 两个界面

| 界面 | 玩家看见什么 | 玩家能做什么 |
| --- | --- | --- |
| 桌面桌宠 | 透明青玉聚宝盆；待机、新 Token 到达、待查看的微光、收获庆祝 | 拖动位置；单击打开收获窗口 |
| Token 收获页 | 本次待收获为主视觉；今日新增、累计 Token 为次要信息；一次聚光与庆祝演出 | 点击“收下”；关闭回到桌宠 |

桌宠不用常驻数字面板。新增到达时短暂提示，悬停时才显示待收量；提示与悬停数字不重复显示。之后保持轻微发光，表示有收获待查看；不能用持续闪烁、弹窗或声音催促。没有新用量不等于 Codex 没在工作，首版不声称展示模型实时思考状态。

收获窗口只有一个主动作，不放导航栏、建筑入口、背包、走势图或任务列表。数值增长时，灵气汇入盆中；点击“收下”，聚宝盆轻浮并散出一圈涟漪。大批用量合并展示，动画时长有上限，不让玩家逐个领取。

连接状态放在收获页底部：等待新用量、已采集、目录不可读或格式暂不支持。首次连接、路径选择、错误处理都在同一页内展开，不单做欢迎页、设置页或诊断中心。托盘只保留显示/隐藏桌宠、打开收获页和退出。

首次打开收获页时直接建立连接；没有新 Token 就明确等待，不用演示数字伪装成真实收益。再次点击桌宠复用已有收获窗口，不重复开窗。

## 4. 首版明确不做

境界、等级、经验、突破、功法、装备、掉落稀有度、背包、图鉴、养成分支、饥饿、战斗、任务、签到、抽卡、多个角色、换装商店、AI 对话。

硬件、小屏模拟器、设备协议、其他 Agent、云同步、账号、联网排行和防作弊也不做。它是私人本地陪伴产品，不把防止用户改存档当成本轮目标。

本轮不另列一套庞大的后续路线。先验证用户是否愿意让桌宠常驻，以及真实 Token 收获是否值得偶尔点开。

## 5. 可靠但小的实现

保留项目约定的 Electron、React + Vite 和 TypeScript，不换框架，不新增 game-core 包。两个窗口通过 loadFile 加载本地资源，采集器直接运行在主进程，通过受限 IPC 通信。桌面端不启动 HTTP 服务，不将浏览器作为交付入口；Fastify 仅保留作诊断和历史接口测试。

```text
本机 Codex 日志
      ↓
唯一采集器：识别新增总量、去重
      ↓
一份本地存档：采集位置、累计、今日统计、已查看位置
      ↓
桌宠状态 + 收获页
```

| 现有位置 | 本轮改动 |
| --- | --- |
| `desktop/` | 复用透明窗口、托盘和窗口通信；明确拖动/单击；确保应用单实例、收获窗口复用 |
| `apps/server/src/companion/collector.ts` | 唯一 Codex 采集器；旧 tracker 和 SessionDriver 不再由应用入口调用 |
| `apps/server/src/companion/save.ts` | 用量、采集进度和已查看位置通过同一保存入口提交；旧档备份与旧累计标注 |
| `apps/web/src/App.tsx` | 收敛成唯一收获页；连接与异常状态就地显示 |
| `scripts/package-desktop.mjs` | 修复 Windows 打包依赖；交付无需开发环境的分发包 |

旧玩法先从启动、界面和结算链路断开，不以删除全部旧源码为交付前提。更新 README 中已过时的 TokenTracker 安装要求。

### 计数规则

- 只读取受支持的本机 Codex 用量日志，不保存对话正文、代码或密钥；首发验证当前 Windows 上实际使用的 Codex 版本。远端和云端会话不自动算作已支持。
- 只用总 Token。按真实日志样本确认累计总量字段和会话身份，再计算新增差额，不把缓存或推理明细重复相加。
- 首次绑定建立基线，不灌入安装前历史；以后重启补读基线之后仍存在的新增日志。日志已被清理时不虚构缺失用量。
- 重复记录、多会话、分叉历史、文件归档或截断、半行写入和累计下降都需处理；不确定的格式停止计数并显示原因，不猜测。
- 约每 5 秒增量检查，完整用量记录出现后争取 10 秒内可见；这不是对模型实时输出速度的承诺。首次扫描之后不反复全量读取历史。
- 用户无需安装或单独启动 TokenTracker；应用启动即启动内置采集。用户仍需正常安装并使用 Codex。

### 最小存档

保存版本号、绑定基线、会话高水位与文件读取位置、累计 Token、按本地日期统计的新增量、已查看累计位置，以及必要的宠物窗口配置。不引入随机种子、物品库、经验表或设备快照。

待收获量由“累计 - 已查看累计位置”得到。“收下”确认的是本次展示的累计快照，期间到达的新 Token 留待下次；重复确认不重复庆祝或影响计数。页面动画不写入任何奖励。

采用单写者、临时文件替换和上一份备份；采集进度与累计不能分开提交。旧存档先备份，旧总量保留为带标签的“旧版累计”，不冒充重新核验过的 Codex 用量，也不重新触发收获；旧资源只保留在备份中。

今日统计优先使用已验证的日志事件时间；无法确认时间的补采只进入累计和本次收获，不全部塞进启动当天。

## 6. 落地顺序

原排期预算按一名熟悉仓库的开发者、复用现有素材估算为 7–10 个工作日，不包含重新制作整套角色美术。以下阶段的代码与自动化部分已经完成，人工试用仍待进行。

| 阶段 | 投入 | 交付与验收 |
| --- | --- | --- |
| 1. 数字可信 | 3–4 日 | 跑通现有程序与打包冒烟；只采 Codex；真实用量进唯一存档；重复读取、重启、并发与分叉不重复入账 |
| 2. 两个界面 | 2–3 日 | 替换洞府页面；桌宠吸纳、待查看、庆祝；收获页展示与确认；新手、等待、异常状态全部内联 |
| 3. 可以交给别人 | 2–3 日 | Windows 分发包、旧档备份、崩溃恢复、睡眠唤醒、高 DPI 与透明窗口点击测试；找 3–5 人短期试用 |

第一阶段先形成可见的 Token 增长链路，第二阶段再加演出。不等复杂美术完成才验证采集。
